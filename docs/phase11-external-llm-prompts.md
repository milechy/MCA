# Phase 11: 外部LLM問い合わせプロンプト集

NemClaw(学習する指揮官)の設計をクロスチェックするための、各LLM向けプロンプト。
それぞれの得意分野に合わせて問いを変えてある。コピペで使える。

---

## 共通の背景ブロック（各プロンプトの先頭に貼る）

```
私は「24時間無人で動く自律コーディングエージェント」を運用しています。現状:

- GitHub Issue または CLI でアイデアを投入すると、LLMが仕様化→コード生成→
  テスト自己修正→PR作成→自動マージ、まで無人で行う。
- 実行は OpenRouter 経由で複数LLMを使い分け。現状のモデル振り分けは
  「難易度→モデル」の固定テーブル:
    trivial/easy → Kimi K2.6 ($0.20/$0.80 per 1M tok)
    medium       → Claude Haiku 4.5 ($1/$5)
    hard         → Claude Sonnet 4.6 ($3/$15)
    architectural→ GPT-5 ($5/$15)
- 難易度は別の安いLLM(DeepSeek V3)が仕様化時に一発で分類している。
- 結果(成功/失敗・コスト・テスト手戻り回数)は JSONL に記録されるが、
  次回のモデル選択には一切フィードバックされない(学習ループが無い)。
- データは追記JSONL + 個別JSONファイルのみ。RDBは未使用(Supabase config だけ存在)。
- 1 PR あたり実コストは約 $0.10、約100秒。1日20 PR を無人処理した実績あり。

やりたいこと:
「指揮官AI」が (a) タスクの難易度判定 と (b) 各タスクに最適なLLMの割り当て を
行い、(c) 過去の結果から学習して精度を上げ続ける。そのために構造・コード・DBを
最適化したい。
```

---

## 1. ChatGPT (GPT-5) 向け — システム設計とトレードオフ

得意: 実装の現実性、段階的移行、コードレベルの具体性

```
[共通背景ブロックを貼る]

質問:
1. 「難易度→固定テーブル」を「過去の成功率/コストから学習する動的ルーティング」に
   進化させる場合、contextual bandit (Thompson sampling / LinUCB) と
   オフライン強化学習、単純なヒューリスティック校正のどれが、この規模
   (1日10-50タスク、月1000-1500件程度)で最も費用対効果が高いですか?
   過剰設計を避けたい。
2. cold-start 問題(学習データが少ない初期)をどう扱うべきか。
   既存の固定テーブルを事前分布として使う設計は妥当か。
3. reward 設計: 成功(+1) − 正規化コスト − 手戻りペナルティ、で十分か。
   見落としがちな reward hacking のリスクは?
4. 「指揮官」を既存の安全境界レイヤー(やってはいけない操作を禁止する番人)と
   どう分離すべきか。意思決定と安全強制を癒着させない設計原則を教えて。
5. この学習ループを実装する最小の段階的ロードマップを、各段階の
   「最初に価値が出るポイント」付きで提案して。
```

## 2. Gemini 向け — データモデルとMLパイプライン

得意: データエンジニアリング、スキーマ設計、特徴量

```
[共通背景ブロックを貼る]

質問:
1. 学習基盤として、追記JSONLからRDB(Supabase/Postgres)に移行する際の
   最小スキーマを設計してください。「ある context(難易度・タスク種別・
   ファイル数・言語・仕様文字数)で、どのモデルが成功率/コスト比で最良か」を
   高速にクエリでき、かつ bandit の事後分布を更新できる形が欲しい。
2. context の特徴量(feature)として、難易度カテゴリ以外に何を取るべきか。
   コーディングタスクの「LLM適性」を予測するのに効く特徴量を、入手しやすさ
   込みで優先度づけして列挙して。
3. 難易度判定そのものを学習で校正したい。planner LLM が予測した難易度 vs
   実際にかかった手戻り回数/コスト、を突合して planner を改善するループの
   データモデルとフィードバック手順を設計して。
4. 1日数十件・月千件規模なら、専用のMLモデルを訓練するより
   集計統計+bandit で十分か、それとも軽量な勾配ブースティング等で
   「このタスクの最適モデル」を分類予測する価値があるか。データ量の観点で判断して。
5. GitHub Actions(ステートレス)とローカルdaemon(ステートフル)の両方から
   同じ学習ストアに書き込む構成の、整合性・冪等性の注意点を挙げて。
```

## 3. Grok 向け — 第一原理での批判とリスク

得意: 前提を疑う、過剰設計への警告、逆張り視点

```
[共通背景ブロックを貼る]

質問(忖度なしで批判的に):
1. そもそも「LLMルーティングを機械学習で最適化する」必要があるのか?
   月1000件規模で、固定テーブル+人間の四半期見直し、で十分ではないか?
   学習システムを入れることの ROI を厳しく評価して。over-engineering の
   臭いがするなら遠慮なく指摘して。
2. モデルの価格・性能は数ヶ月で激変する(新モデル登場、値下げ)。
   過去データで学習した routing policy は、モデル更改のたびに陳腐化する。
   この「非定常環境」で学習する意味はあるのか。むしろ有害ではないか?
3. 「指揮官AIが学習して自律的にモデルを変える」ことの運用リスク
   (静かに悪いモデルに偏る、コスト暴走、デバッグ困難)を最悪ケースで列挙して。
4. もし自分がこのシステムを設計するなら、学習なんか入れずに
   どう「適材適所」を実現するか。最もシンプルで堅牢な代替案を提示して。
5. この構想で、ユーザーが気づいていない致命的な見落としは何か。
```

## 4. Perplexity 向け — 既存事例と最新手法のサーベイ

得意: 出典付きの事実調査、既存ツール比較

```
[共通背景ブロックを貼る]

出典付きで調べてほしいこと:
1. 「LLM router」「model routing」の既存OSS/商用ソリューション
   (例: RouteLLM, Martian, OpenRouter の auto router, NotDiamond,
   Unify, LiteLLM router 等)の比較。それぞれが「タスク難易度→最適モデル」を
   どう決めているか、学習要素の有無、コスト最適化のアプローチを表にして。
2. コーディングエージェント(SWE-agent, OpenHands, Aider, Devin 等)で
   「タスクごとにモデルを使い分ける/学習で選ぶ」実装例はあるか。
   論文・ブログ・リポジトリの出典付きで。
3. contextual bandit を本番のLLMルーティングに使った事例・ベンチマークは
   存在するか。成功例と失敗例の出典。
4. 「LLM-as-judge でタスク難易度を推定する」手法の最新研究と、その信頼性・
   キャリブレーションに関する知見。
5. 我々のように自前で学習ルーターを作るのと、RouteLLM 等の既製品を
   組み込むのと、2026年時点でどちらが推奨されるか。判断材料を出典付きで。
```

## 使い方メモ

- 4つの回答が **一致した点** = 高確度。即採用候補。
- **割れた点**(特に Grok の批判 vs ChatGPT の推進) = そこが本当の意思決定ポイント。人間(あなた)が判断すべき所。
- 特に注目: Grok の Q2(非定常環境で学習する意味)と Perplexity の Q1(既製ルーターで足りるか)。
  この2つが「自作 vs 既製」「学習する vs しない」の分岐を決める。
- 回答が集まったら、このリポジトリの `docs/phase11-nemclaw-brain-readiness.md` の
  §4-5(ロードマップ)を更新する材料にする。
